# お絵かきの草 — 実装仕様書 v3（全作品公開 + いいね・コメント・シェア）

> 前提資料は [oekaki-no-mori-research.md](oekaki-no-mori-research.md)（原作の仕様調査と本質抽出）。
> v1 はエゴコロクイズ単体。v2 で推薦コーナー→投稿画面とひとりでかくを追加。
> v3 で公開の考え方を変えた: **描いた絵は全部ギャラリーに載せ**、いいね・コメント・シェアを
> 常設した。推薦コーナーは「公開の審査」から「賞賛の儀式」になった（下記 §5.1）。

## 0. 最重要方針

- **原作の7モードのうち、まずエゴコロクイズ1本だけを作る。** ただし
  「ゲーム単体に絞ると死ぬ」（研究 命題4／アプリ版が3ヶ月で終了）という教訓があるので、
  **ギャラリー（作品が残る場）を最初から同梱する**。
- **描いた絵は全部ギャラリーに載る。** 対戦でもソロでも、描いた時点で並ぶ。
  命題6（承認は他人経由）は「公開のゲート」ではなく、いいね・コメント・推薦という
  **賞賛の形**で残した。下手な絵ほど面白いゲームなので、公開を恥じる理由がない、
  という判断（命題1: 伝達の誤差が商品）。
- **サーバー権威**。お題の抽選・正誤判定・得点・作品の保存/公開はすべてサーバーが決める。
  クライアントは操作を送り、結果を描くだけ。
- **賭けない・競わない**。IZ は動かさない。レートもランキングも持たない（命題2）。
- **道具を足さない**。フリーハンドのみ。図形・塗りつぶし・レイヤーは入れない（命題3）。

## 1. ゲームルール

| 項目 | 値 | 根拠 |
|---|---|---|
| 人数 | 2〜6人 | 原作どおり |
| 枚数 | 3枚 | 原作は7枚。スマホの1セッション（数分）に合わせた（研究 問題C） |
| 1枚の制限時間 | 60秒 | 原作は60〜180秒 |
| 答え合わせ | 6秒 | |
| 開始条件 | 全員が「じゅんびOK」で自動開始 | 原作の GAME START と同じ |
| 描き手 | ランダム。全員が1周するまで同じ人を選ばない | |
| 描き手拒否 | あり（回答専門で参加できる） | 参加ハードルを下げる装置 |
| むずかしさ | レベル1/2/3。待機中はだれでも変更可、既定は1 | 原作にも難易度選択がある |
| 回答 | チャット欄にひらがなのみ | 原作どおり。ただし入力側で吸収する（§4） |
| 誤答 | ペナルティなし | 命題2 |
| 得点（回答者） | `20 + round(80 × 残り時間の割合)` | 残り時間比例（原作） |
| 得点（描き手） | `30 × 正解者数` | **描き手にも入る**（命題2） |
| ラウンド終了 | 回答者全員が正解、または時間切れ | |
| 最終ラウンド後 | 推薦コーナー(25秒) → 結果 | §5.1 |
| 試合終了 | 3枚。最高得点者が MVP（同点なら全員） | 勝敗を決める場ではない |

お題は [`data/topics.json`](../data/topics.json)（195問）。`label`（描く対象・漢字可）と
`answer`（正解のひらがな）と `alt`（別解）と `level`（1/2/3）を持つ。

**むずかしさ**は原作にならって3段階。1=身近なモノ(ねこ/りんご)、2=組み合わせ・場面
(かんらんしゃ/まんいんでんしゃ)、3=かたちの無いことば(じゆう/あとのまつり/
さいふをおとす)。レベル3は「絵で描けないものをどう描くか」を問うので、
命題1(伝達の誤差)がいちばん濃く出る。`Room.level` は待機中のみ変更でき
(`setLevel`)、`pickTopic` がそのレベルだけから選ぶ。ソロは
`/api/topics/random?level=` で同じ3段階を使う。**描き手には label と answer の両方を渡す**
（漢字のお題があるので「どう書けば正解になるか」が見えないと不公平になる）。
回答者には何も渡さない。

## 2. 画面（縦持ち専用）

```
┌──────────────────────────┐
│ 2/3    ぱん        45    │ ← 何枚目 / お題（描き手のみ） / 残り秒
├──────────────────────────┤
│                          │
│                          │
│      キャンバス           │ ← 縦画面いっぱい。ここが主役
│                          │
│   ┌────────────────┐     │
│   │ ばんそう ねこ   │     │ ← 回答は浮かんで消える吹き出し
│   └────────────────┘     │
├──────────────────────────┤
│ ■■■■■■■■□  ← 描き手のとき  │
│ ●●● もどす  全消し        │
│ ──────────────────────── │
│ 必ずひらがなで入力…       │ ← 回答者のとき
│ [こたえをひらがなで] 送信  │
├──────────────────────────┤
│ ✎あかつき 0  ばんそう 30  │ ← 得点の帯
└──────────────────────────┘
```

原作は横長で「キャンバス・チャット・得点・ツール」の4領域を同時に見せていた（研究 §4.1）。
縦画面では入らないので、**チャットログを捨てて、絵の上に浮かんで消える吹き出しに置き換えた**
（研究 問題B）。「絵が育つ様子」と「回答が飛び交う様子」を同時に見られる、という
体験の核はこれで維持できる。

ソフトキーボードが出ている間は `visualViewport` に追従して `--vh` を縮める。
キャンバスが自動的に縮み、入力欄がキーボードに隠れない。

## 3. 画面遷移

```
boot ──IZ自動ログイン成功──▶ home ──みんなとあそぶ──▶ wait ──全員OK──▶ play
  └──失敗──▶ ゲストログイン ──┘  ├─合言葉で参加─┘        │(最終ラウンド後)
                                 └─ひとりでかく─▶ solo-topic ─▶ solo-draw ─▶ (home)
                                                                 ▼
                                                          recommend(推薦=いいね+コメント)
                                                                 ▼
                              gallery ◀───────────────────────result
```

- `boot`: IZ アプリ内なら自動ログインを試す。失敗したら理由と診断を出し、ゲストログインに落とす。
- `home`: 背景に公開済み作品を `/api/gallery/random` からランダムに数枚、低い不透明度で
  散らして流す（タップは通さない）。滞在の実感を「賑わい」として見せる小さな演出。
- `wait`: 合言葉（4文字）を表示。コピーして共有できる。
- `play`: 描き手はツール、回答者は入力欄。ラウンド終了で答え合わせのかぶせを出す。
- `recommend`: 最終ラウンドの答え合わせのあと、その試合の絵から1人1票で推薦する（§5.1）。
  推薦はその絵へのいいね+コメントとして記録され、結果画面へ進む。
- `result`: 順位と MVP。「もういちど」で同じ部屋の待機に戻る。
- `solo-topic` / `solo-draw`: 対戦とは独立した「ひとりでかく」の入口（§5.3）。
- `shiritori` / `shiritori-draw`: 月間絵しりとり（§5.2）。ホームから入る。
- `gallery`: みんなの作品／自分の作品を切り替えて見る。タップで拡大し、
  いいね・コメント・シェアができる。

## 4. 回答の入力（スマホ化で一番の難所）

研究 問題A のとおり、原作の即答性（3人が同時に別の答えを撃ち合う）は、
キーボードが画面の半分を占める端末では素直に再現できない。取った方針:

1. **入力欄はひらがなに限定する。** ただし弾くのではなく、打ったそばからひらがなに直す。
   カタカナは変換し、漢字・英数・記号は落とす。
   IME の変換中（`compositionstart` 〜 `compositionend`）は触らないので日本語入力を壊さない。
2. **画面に常に「必ずひらがなで入力してください」を出す。**
3. **入力欄をタップするとキーボードが出て、キーボード以外をタップすると引っ込む。**
   `pointerdown` を capture で拾い、`.guessbar` の外なら `blur()` する。
4. **判定は表記ゆれに寛容にする。** 長音の有無、小書き文字、濁点・半濁点の違いを吸収する。
   誤爆より取りこぼしを嫌う（誤答にペナルティがないので、寛容側に倒して困らない）。
5. **送信しても入力欄は閉じない。** 連続で撃てるのがこのゲームの気持ちよさなので。
6. 正解したら入力欄を止めて「せいかい！ +◯◯」に変える。

正規化の実装は `worker/src/kana.js`（判定・権威）と `public/js/kana.js`（入力欄）に
同じものが2つある。**片方だけ変えないこと。**

## 5. 絵の持ち方

**作者IDつきのストローク列**。原作の「荒らしを追放するとその人の描いた線だけが消え、
荒らされた絵が修復される」という仕様（研究 §7）から読み取った形で、
undo・再生・差分同期・将来の追放機能がこれ1つで解ける。

```js
stroke = { id, u: userId, c: 色番号, w: 太さ番号, p: [x0,y0, x1,y1, ...] }
```

- 座標は **キャンバスの幅を 1 とした正規化座標**。x も y も幅で割る。
  端末ごとに画面の縦横比が違っても絵が歪まない。縦長なので y は 1 を超える。
- 縦横比 `ar`（高さ/幅）を作品と一緒に保存し、ギャラリーではその比で再生する。
- 手ブレ補正として、入力座標を直前の点へ 35% 寄せてから記録する。
  画力を補う道具（図形・塗りつぶし）は入れない（命題3）。

### 通信

描き始めに `s0`、描いている間は 60ms ごとにまとめて `s+`、という2種類だけ。
サーバーは検証してから他の参加者へ中継する。

| 種別 | 向き | 内容 |
|---|---|---|
| `s0` | 描き手→サーバー→他 | 新しい線（`id`, 色, 太さ, 最初の点, `ar`） |
| `s+` | 同上 | 続きの点（`id`, 点の配列） |
| `undo` | 同上 | その人の最後の線を1本消す |
| `clear` | 同上 | 全消し |

上限は 1枚あたり 2000本 / 1本 400点 / 合計 60,000点。
クライアントは1本が 380 点に達したら同じ色・太さのまま自動で線を分割するので
(`public/js/draw.js` の SPLIT_POINTS)、長いぐるぐる塗りでも切り詰められない。

### 5.1 推薦コーナー(賞賛の儀式)と、いいね・コメント・シェア

**描かれた絵はラウンド終了のたびに保存され、その時点でギャラリーに載る**（`Db.saveDrawing`）。
公開のゲートは無い。

- **推薦コーナー**（`Room.startRecommend` / 25秒）: 最終ラウンドの答え合わせのあと、
  その試合の絵（最大3枚）が一覧になる。**自分の絵には推薦できない**
  (`Room.recommend` の自薦ガード)。1人1票、コメントは任意（最大80字）。
  投票できる全員が投票し終えたら、25秒を待たずに締め切る。
  1枚も絵が無い試合（`matchDrawings` が空）は推薦コーナーごと飛ばして結果画面へ。
- 締め切り（`Room.finishRecommend`）で、各票は **その絵へのいいね**（`likes` テーブル、
  冪等）と**コメント**（`comments` テーブル、コメントを書いた場合のみ）として記録され、
  `recommendResult`（全3枚ぶんの得票とコメント）を全員に配って結果画面へ進む。
- **いいね**: `POST /api/drawings/:id/like` でトグル。1人1票（主キー
  `(drawing_id, user_id)`）。一覧・単品のレスポンスに `likeCount` / `likedByMe` が乗る。
- **コメント**: `GET/POST /api/drawings/:id/comments`。80字まで。本文は NFKC をかけない
  （全角「！」などを変えないため）。制御文字だけ潰す。
- **シェア**: クライアントで絵を PNG 化し、`navigator.share`（files 対応があれば画像ごと、
  なければテキスト+URL）→ クリップボード、の順に落とす。シェアリンクは `/?drawing=<id>` で、
  開くと `GET /api/drawings/:id`（作品+コメント+いいね状態）で拡大シートをすぐ出す。
- `drawings.posted` / `comments_json` は旧ゲート方式の名残カラム。読み書きしないが、
  既存デプロイの DB を壊さないため定義は残してある。

### 5.2 月間絵しりとり(非同期コンテンツの第一弾。予想型)

研究 問題D「6人同時が集まらない」への答え。**月(JST)ごとに1本のチェーン**を、
リアルタイムに集まらなくてもみんなで繋ぐ。

v1 は「頭文字を教える」方式だったが、それだと前の絵を見る意味がない(頭文字=正解の
一部のネタバレ)という指摘を受け、**予想型**に変えた。伝言ゲームの誤差(命題1)が
そのままゲームの芯になる。

- 見えるもの: **最後の絵だけ**。頭文字もことばも教えない。
- 繋ぎ方: 「まえの絵はなんだとおもう？」(guessedPrev)を自分で予想し、
  **予想の最後の文字**から始まる自分のことば(word)を描いて投稿する。
  サーバーが確かめるのは `shiritoriConnects(guessedPrev, word)`(自己整合)だけで、
  **前の人の実際のことばとは比べない**。ズレてもしりとりは続く。
- 答え合わせ: **ことばが明かされるのは次の人が繋いだとき**。POST のレスポンス
  `revealed: { prevWord, matched }` で「まえの絵は◯◯でした」が返る。
  よって最後尾のことばは常に伏せられ(本人にだけ見える)、予想のネタバレは起きない。
- 参加者のチェーン表示(`revealChain`): **ことばが見えるのは「自分が最後に描いた
  seq まで」**(myLastSeq)。自分が描いたあとに増えた分は？？？のままで、次に自分が
  繋いだとき一気に明かされる。guessedPrev は myLastSeq+1 まで見せる(それは
  「自分のことばがどう読まれたか」であり、未公開のことばのネタバレにならない)。
  guessMatched も同じ範囲で安全。UI は中央の点線に沿って左右交互の数珠つなぎ、
  ことばの受け渡し文字(末尾)を強調、自分のカードは枠色を変える。
- **ギャラリーへの反映**: 投稿時に drawings にも保存(mode: 'shiritori'、topic=word、
  shiritori_entries.drawing_id で紐付け)。答え合わせ前(各月チェーンの最後尾)の絵は
  `Db.maskUnrevealed` がお題を「？？？」に差し替える(作者本人は除く)。
  一覧・ランダム(ホーム背景)・単品取得のすべての口で適用される。
- ルール: ひらがなのみ(最大12字)。word の「ん」終わり不可。guessedPrev の「ん」終わりも
  「前の人は出せないはず」として 400。長音は飛ばす・小書きは大書き・濁点揺れ許容
  (`shiritoriNextChar / shiritoriConnects / shiritoriEndsWithN`)。
  **同じ人は連続でつなげない**(誰かの更新を待つ)。
- 競合: 楽観ロック。POST に `prevSeq` を積み、ズレていれば 409。絵は保持したまま
  新しい絵に予想し直して出せる。
- DB: `shiritori_entries (month, seq UNIQUE, user_id, display_name, word, guessed_prev, strokes_json)`。
- API: `GET /api/shiritori`(今月の状態) / `POST /api/shiritori`。
- 過去月の閲覧は未実装(将来の拡張)。

### 5.3 ひとりでかく

- `GET /api/topics/random` でお題を1つもらう（読みは返さない。判定が無いので不要）。
  気に入らなければ何度でも引き直せる。
- キャンバスは対戦用と同じ `Draw.Board` を流用するが、**時間制限が無い**
  （縦画面いっぱい、道具は常時表示、undo/全消しも同じ）。
- `POST /api/solo-post` に `{ topicLabel, strokes, ar }` を送ると、
  サーバーで一括検証（`sanitizeStrokes`。s0/s+ の逐次検証と同じ上限を一度にかける）した上で
  `mode: 'solo'` として保存する。対戦の絵と同じく、その時点でギャラリーに載る。

## 6. サーバー

Cloudflare Workers + Durable Object。DO は `main` の1個だけ使う
（部屋はメモリ、SQLite も単一。わんわん大戦争と同じ前提）。

- **永続するのは** アカウント・セッション・**作品**だけ。部屋の状態はメモリにしか置かない。
- HTTP API: `/api/iz-config` `/api/login-iz` `/api/login-guest` `/api/me` `/api/stats`
  `/api/gallery`（`mine=1` で自分の作品だけ） `/api/gallery/random`（ホーム背景用）
  `/api/drawings/:id`（単品。シェアリンク用） `/api/drawings/:id/like`（いいねトグル）
  `/api/drawings/:id/comments`（コメント一覧・追加）
  `/api/topics/random`（ソロ用） `/api/solo-post`（ソロの投稿）
  `/api/shiritori`（月間絵しりとりの状態・投稿）
- WebSocket: `/ws?t=<セッショントークン>`。対戦中のメッセージ種別は
  `join / leave / ready / noDraw / s0 / s+ / undo / clear / guess / recommend / restart`。
- **再接続**: スマホは通信が切れやすい。net.js の自動再接続で WebSocket は繋ぎ直るが、
  サーバー側の部屋への関連付け（`Player.ws`）は明示的な `join` でしか戻らないため、
  クライアントは `hello`（=新しい接続が成立するたび）に、直近まで居た部屋へ
  そっと再 join する（`app.js` の `lastRoomCode`）。`Rooms.join` は既存プレイヤーの
  再入室として扱い、対戦の進行は止めない。

### ログイン

IZ アプリ内では `IZ.getIdToken()` の Firebase ID トークンを受け取り、Google の JWK で
RS256 署名検証したうえで `aud` / `iss` / `exp` / `iat` / `sub` を確認する
（`worker/src/firebase-auth.js`）。**`iz:init` の `user.uid` は表示用で偽装できるため使わない。**
わんわん大戦争は Node の crypto と X.509 証明書を使っているが、こちらは Workers 向けに
JWK エンドポイントを使う（X.509 の DER 解析が要らない）。

IZ の外ではゲストログイン。IZ の残高には一切触れない。

## 7. 意図的に入れなかったもの

v2 の「推薦→本人が投稿を選ぶゲート」は v3 で廃止した（全作品公開へ）。
まだ入れていないのは以下:

| 入れなかったもの | 理由 |
|---|---|
| 検定モード（1人用・他人の絵を選択肢で当てる） | ギャラリーが溜まってから。人が集まらない時間帯の答え（研究 問題D）。 |
| 残り6モード | スピード／リレー／めかくし／はやおし／ぬりえ。 |
| 図形ツール・塗りつぶし | 入れると画力差が出て卓が壊れる（命題3）。**今後も入れない。** |
| レート・ランキング | 競技にしない（命題2）。**今後も入れない。** いいね数の順位表も作らない。 |
| スマイルポイント・称号・クレヨン解放 | 原作の育成要素。作品が溜まってからでよい。 |
| 追放・通報・コメント削除 | ストローク列の作者ID・コメントの user_id があるので土台はできている。荒らしが現実になったら入れる。 |
| 絵の非公開設定 | 全作品公開の方針とぶつかる。要望が出たら「自分の絵を消す」から考える。 |

## 8. 受入テスト

`test/flow.test.js` が実際に2人分のクライアントを WebSocket で繋いで1試合通す。

- 合言葉4文字で同じ部屋に入れる
- 1人だけ準備完了では始まらない／全員で始まる
- お題は描き手にだけ渡り、回答者には渡らない
- 描いた線が相手に届く（幅基準の座標なので y > 1 でもそのまま通る）
- 描き手の発言はヒント扱いで、正解にはならない
- 誤答にペナルティがない
- カタカナで打っても正解になる
- 正解で得点が入り、描き手にも入る
- 描き手が交代する
- 3枚で終わると推薦コーナーが開き、全員に同じ一覧が届く
- 自分の絵には推薦できない
- 全員が投票し終えると集計（recommendResult）が配られ、結果画面へ進む
- 描かれた絵は推薦の有無に関わらず全部ギャラリーに載る
- 推薦が「いいね+コメント」としてその絵に残る
- 「じぶんの」一覧（`?mine=1`）は自分の作品だけを返す
- 順位が出て、協調ゲームなので描き手にも回答者にも得点が入る

別のテストで、**ひとりでかいた絵もそのままギャラリーに載る**こと、
**いいねのトグル・未ログイン401・コメント追加・空コメント400・単品取得
（シェアリンク用。likeCount / likedByMe / commentCount 付き）**も確認する。
